# آمادگی انتشار گیشه

تاریخ بررسی: ۲۰۲۶-۱۱-۰۶

نسخهٔ فعلی `1.5.0-rc1` است. بستهٔ موجود برای آزمایش محلی روی x86_64 قابل نصب
و اجراست. انتشار عمومی و اعلام نسخهٔ پایدار هنوز به رفع موارد مشخص زیر نیاز
دارد. نسخه و تاریخ انتشار قبلی بدون اعلام انتشار جدید حفظ شده‌اند.

## تغییرات انجام‌شده در پروژه

### بررسی نسخه، بسته و لینک‌ها

ابزار `build-aux/check-release.py` اضافه شد. اجرای عادی آن این موارد را بررسی می‌کند:

- فرمت نسخه و تاریخ، نبود تاریخ آینده و تطابق عنوان changelog؛
- استفادهٔ AppStream از نسخه و تاریخ اصلی پروژه؛
- تطابق نوع `development` با نسخهٔ RC و نوع `stable` با نسخهٔ پایدار؛
- شناسهٔ برنامه و نام launcher در manifest؛
- در صورت دریافت tag، برابری دقیق آن با `v<VERSION>`.

گزینهٔ `--artifacts` محتویات `SHA256SUMS` و `build-info.json`، checksum واقعی
هر دو فایل، معماری، runtime و commit را کنترل می‌کند. سپس تک‌تک فایل‌های
آرشیو سورس، حالت اجرایی فایل‌ها و symlinkها را با خروجی جدید `git archive HEAD`
مقایسه می‌کند. مسیر ناامن، ورودی تکراری و بستهٔ دست‌کاری‌شده رد می‌شوند.
این بررسی تطابق سورس را ثابت می‌کند؛ ساخت باینری از آن سورس به شواهد مستقل
روند ساخت نیاز دارد.

گزینهٔ `--public-urls` لینک‌های AppStream و تصویر معرفی را بدون احراز هویت
بررسی می‌کند. این کنترل برای انتشار عمومی باید موفق باشد. در وضعیت فعلی،
شکست آن به دلیل دسترسی‌ناپذیربودن لینک‌های مخزن خصوصی انتظار می‌رود.

۱۲ تست جدید برای کنترل نسخه، tag اشتباه، تاریخ آینده، نوع انتشار، صحت بسته،
سورس تغییرکرده با checksum جدید، commit اشتباه، checksum تکراری، مسیر ناامن
آرشیو و لینک عمومی اضافه شد.

### آزمون بستهٔ نصب‌شده

ابزار `build-aux/smoke-flatpak.py` بسته را در یک نصب کاربری موقت نصب می‌کند؛
نصب معمول Flatpak کاربر را تغییر نمی‌دهد. این ابزار:

- از runtime ازپیش‌نصب‌شدهٔ سیستمی استفاده می‌کند؛
- شبکهٔ فرایند برنامه را قطع می‌کند؛
- فقط پوشهٔ تست را به‌صورت فقط‌خواندنی در اختیار برنامه می‌گذارد؛
- برنامه را در فارسی و انگلیسی با Xvfb و D-Bus اجرا می‌کند؛
- وجود launcher، آیکن‌های اصلی و symbolic، مجوز، AppStream و desktop را بررسی می‌کند؛
- اولین اجرا، ورود به حالت محلی، ذخیرهٔ وضعیت، resource، ترجمه و جهت نوشتار را کنترل می‌کند.

برای این آزمون، GNOME Platform مطابق manifest باید به‌صورت سیستمی موجود باشد.
آزمون خودکار عمداً از پنجرهٔ انتخاب فایل، ورود واقعی حساب و Wayland استفاده
نمی‌کند؛ این موارد شواهد جداگانه لازم دارند.

### روند CI و بسته‌بندی

workflow قبلی اکنون ابزارهای ساخت را هم lint می‌کند و کنترل نسخه و ماتریس
اندازه‌های پنجره در هر دو زبان را اجرا می‌کند.

workflow جدید `.github/workflows/flatpak.yml` برای اجرای دستی یا tag نسخه آماده است.
روی دو runner مستقل x86_64 و aarch64، GNOME SDK و runtime را نصب می‌کند،
بسته را از commit checkout‌شده می‌سازد، صحت آرشیو را بررسی می‌کند و همان
بسته را داخل sandbox اجرا می‌کند. فایل‌ها پس از موفقیت به‌عنوان Actions artifact
نگهداری می‌شوند. این workflow خودکار GitHub Release عمومی ایجاد نمی‌کند.

اسکریپت بسته‌بندی پیش از شروع ساخت، هماهنگی نسخه را کنترل می‌کند و runtime
گزارش‌شده را از manifest می‌خواند؛ مقدار نسخهٔ runtime دیگر در گزارش hardcode نشده است.

## مانع فعلیِ دسترسی عمومی

درخواست بدون احراز هویت به مخزن و تصویر اصلی AppStream پاسخ `404` داد.
بررسی احرازهویت‌شدهٔ `gh repo view` تأیید کرد که مخزن
`arashe023/Gisheh` مقدار `isPrivate: true` دارد و شاخهٔ اصلی آن `main` است.
اجرای بعدی کنترل تصویر نیز timeout داشت؛ هیچ‌کدام نتیجهٔ موفق محسوب نشده‌اند.

برای انتشار عمومی باید یا همین مخزن پس از بررسی محتوا عمومی شود، یا سورس،
مستندات، تصویر و بسته‌ها در مقصد عمومی مناسب قرار بگیرند و لینک‌های AppStream
و README اصلاح شوند. عمومی‌کردن مخزن دسترسی به تاریخچهٔ آن را هم تغییر می‌دهد
و به تصمیم صریح مالک نیاز دارد؛ وضعیت دسترسی مخزن در این کار تغییر نکرد.

## وضعیت بستهٔ موجود

فایل‌های موجود در `dist/` از قبل حاضر بودند و در این بررسی دوباره آزمایش شدند:

- `Gisheh-1.5.0-rc1-x86_64.flatpak`
- `Gisheh-1.5.0-rc1-source.tar.gz`
- `SHA256SUMS`
- `build-info.json`

commit بسته `d7a530a5630ba1fbb11e58161878125aef3174fb` و روش ساخت آن
`native-pure-python` است. runtime مورد آزمایش
`org.gnome.Platform/x86_64/50` بود. تغییرات جدید ابزارها و مستندات هنوز commit
نشده‌اند و داخل این آرشیو قدیمی نیستند. پس از ثبت سورس نهایی باید بسته و
آرشیو دوباره از همان commit ساخته شوند؛ ابزار بسته‌بندی روی working tree
تغییریافته عمداً ساخت را متوقف می‌کند.

## دستورهای تکرار بررسی

از ریشهٔ پروژه اجرا شوند:

```sh
ruff check src tests build-aux
python3 build-aux/check-release.py
python3 build-aux/check-release.py --tag v1.5.0-rc1
python3 build-aux/check-release.py --artifacts dist
python3 build-aux/check-release.py --public-urls

meson setup /tmp/gisheh-release-build --prefix=/tmp/gisheh-release-install
meson compile -C /tmp/gisheh-release-build
meson test -C /tmp/gisheh-release-build --print-errorlogs
meson test -C /tmp/gisheh-release-build gtk-tests --repeat=2 --print-errorlogs
msgfmt --check --statistics -o /tmp/gisheh-fa.mo po/fa.po
meson install -C /tmp/gisheh-release-build

LANG=C.UTF-8 LANGUAGE=fa GISHEH_SMOKE_MATRIX=1 \
  GSK_RENDERER=cairo GDK_BACKEND=x11 \
  xvfb-run -a -s '-screen 0 1920x1080x24' dbus-run-session -- \
  python3 tests/installed_smoke.py /tmp/gisheh-release-install

python3 build-aux/smoke-flatpak.py dist/Gisheh-1.5.0-rc1-x86_64.flatpak
git diff --check
```

برای ساخت بستهٔ جدید، پس از ثبت همهٔ تغییرات نهایی و تمیزشدن working tree:

```sh
python3 build-aux/package-flatpak.py
python3 build-aux/check-release.py --artifacts dist
python3 build-aux/smoke-flatpak.py dist/Gisheh-1.5.0-rc1-x86_64.flatpak
```

روش جایگزین `--native` فقط برای بستهٔ آزمایشی مستقل است؛ نتیجهٔ موفق آن
به‌جای تأیید ساخت با SDK یا پذیرش Flathub گزارش نشود.

## آزمون‌های باقی‌مانده پیش از نسخهٔ پایدار

۱. روی دسکتاپ Wayland واقعی بسته را اجرا کنید؛ ورود محلی، جست‌وجو، جزئیات،
تنظیمات و رفت‌وبرگشت بین نماها را در فارسی و انگلیسی بررسی کنید.

۲. با کتابخانهٔ آزمایشی، export و import را از portal انجام دهید. لغو انتخاب،
فایل نامعتبر، جایگزینی کتابخانه و بازیابی پشتیبان باید دادهٔ موجود را طبق
تأیید کاربر حفظ یا جایگزین کنند.

۳. در نسخهٔ قبلی چند عنوان و امتیاز ذخیره کنید، برنامه را ببندید، بستهٔ جدید
را نصب کنید و حفظ داده و امکان بازکردن دوبارهٔ برنامه را بررسی کنید.

۴. اتصال خواندنی TMDB، تصویر، جست‌وجو و تغییر زبان محتوا را از شبکهٔ مقصد
آزمایش کنید. خطای اتصال این محیط اثبات خرابی کلید نیست و موفقیت قدیمی هم
تأیید دسترسی امروز نیست.

۵. ورود، نگهداری token در Secret Service، همگام‌سازی و خروج Simkl را فقط با
حساب اختصاصی آزمایش انجام دهید. از سابقهٔ شخصی برای تست نوشتن استفاده نشود.

۶. پیمایش کامل با صفحه‌کلید و screen reader، focus قابل مشاهده، برچسب
کنترل‌های فقط‌آیکن و متن بزرگ را در همهٔ پنجره‌های مهم بررسی کنید.

۷. CI و ساخت SDK هر دو معماری را روی سورس نهایی اجرا و نتایج را بررسی کنید.
برای نسخهٔ پایدار، `VERSION`، `RELEASE_DATE`، changelog و نوع انتشار AppStream
هم‌زمان تغییر کنند؛ سپس tag تازه و بستهٔ دقیق همان revision منتشر شوند.

## مسیر Flathub

طبق [الزامات Flathub](https://docs.flathub.org/docs/for-app-authors/requirements)
که در تاریخ این بررسی خوانده شد، محتوای تولیدشده یا کمک‌گرفته از AI نباید در
manifest ارسالی باشد؛ ارسال PR و متن تعاملات بررسی نیز باید انسانی باشد.
سهم محتوای تولیدشده در برنامه و بسته‌بندی باید با ذکر بخش‌ها و حدود آن افشا شود.
manifest توسعهٔ فعلی جای manifest ارسال را نمی‌گیرد.

مراحل رسمی شامل ساخت و اجرای واقعی، بررسی مجوزها و permissionها، lint رسمی
manifest و repository و بررسی انسانی است؛ جزئیات در
[راهنمای ارسال Flathub](https://docs.flathub.org/docs/for-app-authors/submission)
آمده است. بستهٔ مستقل نیز به‌تنهایی مسیر به‌روزرسانی خودکار فراهم نمی‌کند؛
این تفاوت در [مستندات Flatpak](https://docs.flatpak.org/en/latest/single-file-bundles.html)
توضیح داده شده است.
